Architecture Approaches for Multi-Tenant GLAdmin

Three ways to add multi-tenant + admin + payments. Click to select your preference.

Approach A: Prisma Middleware (Recommended)

// Single middleware intercepts all queries
prisma.$use(async (params, next) => {
  if (shouldFilter(params.model)) {
    params.args.where.organizationId = currentOrgId;
  }
  return next(params);
});

Pros

  • One line of code per query type
  • Can't forget the filter (always applied)
  • Works with existing services unchanged
  • Easy to bypass for super admin

Cons

  • Middleware runs on every query (implicit)
  • Harder to debug when filter is wrong

Prisma Middleware

Approach B: Base Service Pattern

class BaseService {
  protected orgFilter(): PrismaFilter {
    return { organizationId: getOrgId() };
  }
}

// Each service must call orgFilter() explicitly
findAll() {
  return prisma.supplier.findMany({
    where: { ...this.orgFilter() }
  });
}

Pros

  • Explicit — you see the filter in every query
  • No magic, easy to debug
  • Easy to customize per service

Cons

  • Must remember to add filter to every new query
  • More boilerplate, more code changes
  • Easy to accidentally skip (data leak risk)
B

Base Service

Explicit per-query filter via base class, more code but visible

Approach C: Hybrid — Middleware + Service Methods

// Middleware catches 95% of queries
prisma.$use(autoOrgFilter);

// Service can bypass or customize:
findAllForSuperAdmin() {
  return prisma.supplier.findMany({
    where: { /* bypass middleware */ }
  });
}

Pros

  • Middleware for safety (can't forget)
  • Service methods for exceptions
  • Best of both worlds

Cons

  • Slightly more complex mental model
  • Need clear convention for when to use which
C

Hybrid

Middleware default + service overrides for special cases
